Lesson 0013

Relationships: cardinality, direction, active paths

Model the dataAbout 20 minSkill: configure a relationship

After this lesson you can configure a relationship's cardinality and cross-filter direction from the data and the filtering requirement.

Why this matters for the exam

Relationships sit under every DAX answer: a measure can only be as right as the filters that reach it. In practice questions this topic appeared as "the total repeats for every supplier", "which cardinality?" and "why doesn't this key relate?". Each is a two-minute win once you know the three settings: cardinality, direction, active or not. That moves you toward passing PL-300.

Recall first

From lesson 0012 (star schema): which table type holds the numbers you sum, and why must a dimension key be unique?

Show answer

The fact table holds the measurable events; dimensions hold descriptive attributes. A unique key on the dimension is what makes the relationship one-to-many (see star schema guidance).

Core idea

A relationship tells the engine how a filter on one table reaches another. Two columns, one setting for cardinality, one for cross-filter direction, and a flag for active.Source: Model relationships.

Direction. Filters flow from the one side to the many side. Single is the default and the recommendation. Both lets the many side filter the one side too. Reserve it for specific needs, such as a bridge table or a slicer that should show only items with data, because it can create ambiguous paths and slower queries.See Bidirectional filtering guidance. For security, RLS filters follow relationships one way unless you tick "Apply security filter in both directions" (lesson 0036; RLS docs).

Active or inactive. Between two tables only one relationship is active (one active path). The others are inactive and drawn dashed. An inactive relationship filters nothing until a measure calls USERELATIONSHIP, covered in lesson 0014.Active vs inactive relationships.

Keys must share a data type. Text "101" does not relate to whole number 101; change the type in Power Query or the column tools first.Create and manage relationships. In DirectQuery you can also tick "Assume referential integrity" so Power BI uses faster inner joins.

Symptom to cause: the same total repeated on every row of a supplier table means the filter cannot reach the fact table. Fix the relationship or its direction, not the measure.

Practical example

Context. Purchasing wants sales by supplier. A product can have several suppliers and a supplier several products, so the pairs live in Supplier_Product (one row per pair). Sales relates to Product.

  1. Relate Supplier[SupplierID] (1) to Supplier_Product[SupplierID] (*), single direction.
  2. Relate Product[ProductID] (1) to Supplier_Product[ProductID] (*) and set the cross-filter direction to Both.
  3. Keep Product (1) to Sales (*) single.
Total Sales = SUM ( Sales[Amount] )

Result. A table of Supplier[Name] and [Total Sales] now shows a different value per supplier. Before step 2 the filter stopped at the bridge (one-to-many only flows downhill), so every supplier showed the grand total. Only the one relationship is bidirectional, which limits the ambiguity risk.

Traps

Wrong: "Set Both just in case." Right: Single is the default; Both slows queries and can create ambiguity. Use it for a stated need.

Wrong: "Many-to-one means many-to-many." Right: If the dimension key is unique the relationship is many-to-one. Many-to-many is only for repeats on both sides.

Wrong: "The inactive relationship will filter anyway." Right: It does nothing without USERELATIONSHIP in the measure.
