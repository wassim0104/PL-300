Lesson 0022

Optimise model performance

ModelAbout 20 minAfter this lesson you can diagnose a slow report with Performance Analyzer and DAX query view, and shrink a model without breaking the required visuals.

Why this matters for the exam

Performance questions are scenario-based: a big PBIX, a slow page, a requirement you must not break. The right answer almost always removes data before load or reads Performance Analyzer correctly. It is a steady source of marks in the Model the data domain.

Recall first

Where is a calculation-group item written, and what does it use to refer to the measure in the visual?

In the semantic model's calculation group; it uses SELECTEDMEASURE().

Core idea

Shrink the model (Import mode).Data reduction techniques.

  • Remove unused columns, the biggest win, and unneeded rows (old history, cancelled orders) in Power Query. Hiding a column does not shrink the model. Keep columns that visuals, relationships or distinct counts need.
  • Reduce cardinality. GUIDs, DateTime to the second, free text and concatenated keys compress badly. Split DateTime into Date and Time. Keep one integer key and drop a redundant GUID. Round only when the requirement loses nothing. Changing DateTime to Date loses the hours, and a format change alters display, not storage.
  • Lower granularity: group to the grain the report needs (daily, not transaction) or add an aggregation table.Aggregations. Disable auto date/time. Do calculated columns in Power Query or the source.

Find the slow part. Performance Analyzer (Optimize ribbon) records, per visual, DAX query, Visual display and Other time.Performance Analyzer. High Other means the visual waited on other visuals, so reduce visuals per page (25 or more is slow) or fix the slow neighbours. Copy query sends the DAX to DAX query view, where you test and tune with EVALUATE.DAX query view. Bidirectional relationships and heavy iterators over large facts also hurt.

Practical example

Business context: a 550 MB PBIX with a 12-million-row fact table is slow to open and refresh. The visuals cover the last three years and count distinct customers.

  1. Remove Description, RowGUID and the unused TaxAmt in Power Query.
  2. Split OrderDateTime into Date and Time columns.
  3. Filter rows to the last three years.
  4. Keep CustomerKey: the distinct-customer count needs it.
  5. Run Performance Analyzer before and after to confirm the gain.
= Table.SelectRows(Source, each [OrderDate] >= Date.AddYears(Date.From(DateTime.LocalNow()), -3))

Why it works: every step removes data before it is loaded, so the engine stores fewer rows and fewer distinct values, while everything the visuals use remains.

Traps

Wrong belief: Hiding a column or applying OLS reduces model size.
Correct rule: Both keep the data loaded. Only removing it before load shrinks the model.

Wrong belief: Remove CustomerKey too, it is just a key.
Correct rule: If a visual counts distinct customers or a relationship uses it, removing it breaks the report.

Wrong belief: Tune the slow visual's DAX when its time is mostly Other.
Correct rule: Other is waiting on other visuals. Reduce visuals or fix the slow neighbours.
