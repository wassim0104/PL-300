Gateways, scheduled refresh and incremental refresh

Manage and secureAbout 20 min

After this lesson you can decide whether a gateway is needed, order the steps to schedule refresh, and use incremental refresh to cut refresh volume.

Why this matters for the exam

Refresh and gateway questions turn up often, typically as "which source needs a gateway" or "order these steps". The rules are few and mechanical, so this is a topic where careful study converts straight into points.

Core idea

An on-premises data gateway is needed when the service cannot reach the data directly: on-premises SQL Server, files and shares, SSAS live connections, and sources in a private VNet (or use a VNet data gateway). It is not needed for internet-reachable cloud sources: Azure SQL with public access, SharePoint Online, OneDrive for work, web. Glossary: gateway.

Standard mode: shared, multi-user, supports DirectQuery and live connections. Personal mode: one user, Import only.

Steps to schedule refresh, in order:

  1. Install and register the gateway.
  2. Add a data source on the gateway with credentials.
  3. Publish the model.
  4. Map the model to the gateway connection.
  5. Configure scheduled refresh.

Server and database names in the PBIX must match the gateway data source, otherwise the gateway cannot be selected.

Scheduled refresh: up to 8 per day on shared capacity (Pro), 48 on Premium or Fabric capacity. It is paused after two months of inactivity; opening a report on the model resumes it. DirectQuery and live models need no scheduled data refresh, and dashboard tiles have their own cache refresh.

Incremental refresh: create DateTime parameters named exactly RangeStart and RangeEnd, filter the table on them (the filter must fold), then set a policy in Desktop: archive N years, refresh the last N days. It takes effect after publishing and cuts refresh time and gateway transfer. Aggregations and automatic page refresh do not.Refresh failures notify the owner; credentials are set in the model settings in the service.

Practical example

An on-premises SQL model must refresh at 7 AM.

  1. Install a standard-mode gateway on a server.
  2. Add the SQL data source, using the same server and database names as the PBIX.
  3. Publish the model.
  4. Model settings > Gateway connection: map to that data source.
  5. Scheduled refresh: on, 07:00.
#"Filtered Rows" = Table.SelectRows(Source,
    each [OrderDate] >= RangeStart and [OrderDate] < RangeEnd)

The filter above is the incremental refresh step. Use >= on one parameter and < on the other so no row loads twice. It works because the service can now fetch only the recent partitions through the gateway.

Traps

Wrong: Azure SQL or SharePoint Online needs a gateway. Right: Internet-reachable cloud sources do not.

Wrong: Scheduling refresh keeps a DirectQuery or live SSAS model current. Right: Those query the source live, so nothing needs refreshing.

Wrong: Aggregations reduce gateway transfer for Import. Right: Incremental refresh does.
