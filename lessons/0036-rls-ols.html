Lesson 0036

Row-level and object-level security

Manage and secureAbout 20 min

After this lesson you can implement static and dynamic RLS, assign members (preferably groups), test it, and predict what a user in several roles sees.

Why this matters for the exam

Row-level security is the single most tested security topic: expect several questions, usually on dynamic filters, union versus intersection, or who is affected. Finishing it also completes the Manage and secure domain, so the next stop is your first mock exam.

Recall first

Which workspace roles bypass RLS?

Show answer

Admin, Member and Contributor. RLS applies to Viewers, app consumers and shared-item recipients.

Core idea

Workflow: Desktop > Modeling > Manage roles (define DAX table filters) > publish > service > model > Security (add members) > Test as role. You cannot assign members in Desktop.Row-level security with Power BI Terms: RLS, dynamic RLS.

Static: [Region] = "West", one role per value. Dynamic: [Email] = USERPRINCIPALNAME(), one role for everyone, driven by a user column. In Desktop USERNAME() returns DOMAIN\user, in the service both return the UPN, so prefer USERPRINCIPALNAME().

SituationResult
Filters on several tables in one roleAND (intersection)
A user in several rolesUnion: rows allowed by either

Members can be users, security groups, mail-enabled security groups and distribution groups, not Microsoft 365 groups. Use Microsoft Entra groups so another team (for example IT security) controls access without content rights; moving a manager to another region is a group change, not a DAX change.

RLS applies to Viewers, app consumers and shared-item recipients, even with Build (Analyze in Excel). Filters flow one way along relationships by default; to reach the one side through a bridge tick Apply security filter in both directions (glossary). Test as role / "Now viewing as" checks roles or a person; for dynamic RLS test as the person, since a role alone uses your own identity.

Live connection to Analysis Services: define RLS in the AS model. DirectQuery can use source security with SSO. Object-level security hides tables or columns (and their metadata) per role, set with external tools such as Tabular Editor. RLS cannot hide columns.

Practical example

Regional sales managers see only their own region; one role must serve all of them.

-- Role "Sales Managers" on table Region
[ManagerEmail] = USERPRINCIPALNAME()

Publish, add the managers' Entra security group to the role in the service, then use Test as role with a specific manager. And for an intersection inside one role:

-- Role "Germany Management"
DimSalesTerritory: [Region] = "Germany"
DimCustomer:       [Occupation] = "Management"

Both filters sit in one role, so users see only German management customers. Two separate roles would show Germany rows plus management rows.

Traps

Wrong: Two roles give an intersection. Right: You get a union. Put both filters in one role.

Wrong: RLS restricts workspace Members and Contributors. Right: It applies to Viewers only.

Wrong: Add a Microsoft 365 group, or assign members in Desktop. Right: Use security groups, and assign in the service.
