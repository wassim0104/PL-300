Lesson 0008

Merge vs append, and choosing the join kind

Prepare the dataAbout 20 minSkill: pick merge or append and the right join kind

After this lesson you can decide between merge and append, pick the join kind from the requirement’s wording, and keep helper queries out of the model.

Why this matters for the exam

Combining queries is one of the most reliable PL-300 topics: nearly every practice set has a question that hinges on the join kind or on append versus merge. The wording of the requirement (“customers without sales”, “keep all products”) tells you the answer, so this is cheap points once you learn to read it.

Recall first

In Power Query, which of Split by delimiter’s options gives one value per row?

Show answer

The Advanced option “into rows”; the default produces columns.

Core idea

Append stacks rows from tables with the same or similar columns; columns missing on one side become null. Use Append Queries as New to keep the originals. Append queries. Merge adds columns from a related table by matching key columns, like a SQL join, and returns a nested table column that you expand. Merge queries overview.The match keys must have the same data type, or nothing matches.

Join kindReturnsTypical wording
Left outer (default)All left rows plus matches“keep all customers”
Right outerAll right rows plus matchesmirror of left
Full outerAll rows from both“everything from both”
InnerMatching rows only“only those in both”
Left antiLeft rows with no match“customers without sales”
Right antiRight rows with no matchmirror of left anti

Order matters in two places. Remove duplicates after appending, because duplicates across the two tables only appear once they share a table. And use Merge as New with Enable load turned off on the sources: that gives the smallest model, and the sources must not be deleted because the merge references them.Fuzzy matching is optional for text keys. Flattening a snowflake (Product, Subcategory, Category) with merges makes one Product dimension: use Inner when the link always exists and Left outer when the requirement says to keep all products. Glossary: Merge, Append, Left anti join.

Practical example

Marketing wants a list of customers who never bought anything. You have Customers and Sales, both keyed on CustomerID.

  1. Home, Merge Queries as New. Left table Customers, right table Sales, select CustomerID in both.
  2. Join kind: Left anti (rows only in first).
  3. Remove the empty nested Sales column if it appears.
  4. Right-click Customers and Sales, clear Enable load (if nothing else needs them).
Merged = Table.NestedJoin(Customers, {"CustomerID"}, Sales, {"CustomerID"},
    "Sales", JoinKind.LeftAnti)

Left anti keeps exactly the left rows with no match, so the answer is the list itself. The sources stay as connection-only queries, so the model holds one table instead of three.

Traps

Wrong belief: “append can bring address columns onto customers.” Correct rule: append adds rows; merge adds columns.

Wrong belief: “inner join is the safe default.” Correct rule: if the requirement says to include customers without addresses, use Left outer; Inner drops them.

Wrong belief: “I can leave the intermediate queries loaded.” Correct rule: loaded helper queries duplicate data in the model; disable load instead of deleting.
