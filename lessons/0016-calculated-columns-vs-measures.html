Lesson 0016

Calculated column, measure or calculated table?

Model the dataAbout 18 minSkill: choose the right calculation type

After this lesson you can choose between a calculated column, a measure and a calculated table for a requirement, and explain why from row context versus filter context.

Why this matters for the exam

"Which should you create: a calculated column, a measure or a calculated table?" is one of the most repeated DAX questions in practice tests, and it hides the two ideas that the next two lessons build on: row context and filter context. Get the choice right and you also get the vocabulary right.

Recall first

From lesson 0015: which property stops a Year column from being summed in a visual?

Show answer

Set the column's default summarization to Don't summarize.

Core idea

Two evaluation contexts decide what a DAX expression sees. Keep them apart now; lessons 0017 and 0018 show how they interact.

Row contextFilter context
What it is"The current row" of one table. Lets you read that row's columns.The set of filters on columns that decides which rows an aggregation can see.
Where it comes fromCalculated columns; iterators such as SUMX.Visual rows and columns, slicers, filter pane, and CALCULATE.
Does it filter tables?No. It does not filter anything and does not follow relationships (except through RELATED).Yes, and it follows relationships (lesson 0013).

That gives the decision rule.See Calculated columns and the DAX overview.

ObjectEvaluatedContextStored?Use for
Calculated columnAt refreshRowYes (memory)Something to slice or filter by: size band, "Inactive - " & name
MeasureAt query time, per cellFilterNoAggregates, ratios, KPIs, % of total
Calculated tableAt refreshWhole table expressionYesCalendars, number ranges, role-playing copies
  • Ratios must be measures. DIVIDE ( SUM ( T[EBITDA] ), SUM ( T[Revenue] ) ) sums first, then divides. A ratio column averaged in a visual gives the wrong answer.
  • Implicit measure: made when you drag a numeric column into Values (default summarization). Explicit measure: written in DAX; reusable, and required by calculation groups.
  • Calculated tables (docs): CALENDAR; GENERATESERIES ( -100, 100, 1 ) for numbers or what-if (GENERATESERIES); SUMMARIZE ( 'Date', 'Date'[Year], 'Date'[Quarter] ) for distinct combinations (SUMMARIZE); Ship Date = 'Date' for a role-playing copy.
  • If Power Query or the source can do it, do it there. Upstream columns compress better than DAX columns.

Practical example

Context. Finance wants an EBITDA margin on a card that reacts to slicers, and a Size band slicer on each order line.

-- Measure: filter context, query time
EBITDA Margin = DIVIDE ( SUM ( T[EBITDA] ), SUM ( T[Revenue] ) )

-- Calculated column on Orders: row context, refresh time
Size band =
SWITCH (
    TRUE (),
    Orders[Amount] < 100,  "Small",
    Orders[Amount] < 1000, "Medium",
    "Large"
)

Why it works. The margin has no meaning for a single row; it must be computed for whatever rows the card's filter context selects. The band is a property of each row, you need it to slice by, and it must exist as a column before any slicer is touched. In SWITCH ( TRUE (), ... ) the first true condition wins, so order them so each boundary falls in exactly one band. A band is also a good Power Query conditional column.

Traps

Wrong: "Put margin % in a calculated column." Right: Ratios are measures (sum, then divide).

Wrong: "Calculated columns respond to slicers." Right: They are fixed at refresh. Only measures react to filter context.

Wrong: "ADDCOLUMNS groups rows." Right: It adds columns to every row. Use SUMMARIZE or VALUES for distinct combinations.
